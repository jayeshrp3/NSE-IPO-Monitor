# Data Model: IPO Deadline Tracker

## Core Entity: IPO

The core entity in the application is the IPO record.

### SQLite Table

The `ipos` table stores only source fields and timestamps:

| Column | SQLite type | Constraint |
|---|---|---|
| `id` | INTEGER | Primary key |
| `company_name` | TEXT | Required; reject blank after trimming |
| `opening_date` | TEXT | Required ISO `YYYY-MM-DD` date |
| `closing_date` | TEXT | Required ISO `YYYY-MM-DD`; not earlier than opening |
| `allotment_date` | TEXT | Nullable ISO `YYYY-MM-DD` |
| `refund_date` | TEXT | Nullable ISO `YYYY-MM-DD` |
| `listing_date` | TEXT | Nullable ISO `YYYY-MM-DD`; subject to three-weekday rule |
| `created_at` | TEXT | Required ISO 8601 UTC timestamp |
| `updated_at` | TEXT | Required ISO 8601 UTC timestamp |

Database constraints should enforce required values and the opening/closing
sequence. Calendar validity and the listing-date weekday rule are also checked
before persistence in the validation/service layer.

### Fields

- `id`: unique record identifier, generated by the database
- `company_name`: required display string; rejected if blank after trimming; retain the user's display spelling
- `opening_date`: required date
- `closing_date`: required date
- `allotment_date`: optional date
- `refund_date`: optional date
- `listing_date`: optional date
- `created_at`: timestamp set at insertion
- `updated_at`: timestamp updated on every modification

### Derived Values

These values are computed from the current date and validated fields and are not treated as the canonical source of truth:

- `status`: one of `Upcoming`, `Open`, `Closed`, or `Listed`
- `days_remaining`: signed calendar-day difference `closing_date - current_date`; positive before close, zero on closing date, and negative after close
- `expired_days`: positive elapsed calendar days after closing; null while the IPO is not expired
- `alert_status`: `Expired` after closing, `Approaching` only for an Open IPO within the configured inclusive threshold, or `None` otherwise

### Validation Rules

- `company_name` must be present after trimming and whitespace normalization.
- `opening_date` and `closing_date` are required.
- `closing_date` must be on or after `opening_date`.
- `listing_date`, if supplied, must be on or after the date three working days strictly after `closing_date`. Working days are Monday-Friday; Saturday/Sunday are skipped, public holidays are not.
- `allotment_date`, `refund_date`, and `listing_date` are optional and may be blank.
- Date parsing must reject malformed values and invalid calendar dates.
- Alert threshold is read from `IPO_ALERT_THRESHOLD`, defaults to 3, and must be a non-negative integer. Invalid configuration must fail explicitly.
- Duplicate identity is normalized company name plus opening and closing dates. Normalize only by trimming leading/trailing whitespace, collapsing repeated internal whitespace, and case-folding for comparison. Reject a duplicate with a clear error.
- Updates preserve optional dates whose fields are omitted; an explicitly empty optional date clears that value.

### Relationships

There are no child entities or foreign keys required for the initial Part 1A scope. The system uses a single IPO table with all required fields and optional milestone dates.

### Lifecycle / State Model

- New object: record is created with validated required fields.
- Active object: record remains in the dataset and is re-evaluated whenever the list is viewed.
- Updated object: optional fields may be cleared or changed while preserving existing values when fields are omitted.
- Deleted object: records remain available until the user explicitly confirms deletion.

### Normalization and Duplicate Rules

- Duplicate comparison trims leading/trailing whitespace, collapses repeated internal whitespace, and case-folds the name; the stored display name is not rewritten by duplicate normalization.
- Duplicate detection compares normalized company name plus opening and closing dates.
- Duplicate records must be rejected before database insertion.

### Date and Corruption Behavior

- Status boundaries are inclusive for opening and closing dates as Open, and
  inclusive for the listing date as Listed.
- The signed `days_remaining` value is exposed as derived data. When it is
  negative, the user-facing view shows an expired indicator and positive
  `expired_days`, not a positive countdown.
- `alert_status` is `Expired` after closing, `Approaching` only when Open and
  within the configured inclusive threshold, and `None` otherwise.
- If persisted data is malformed, the application must surface a safe,
  actionable error and must not invent a status or silently rewrite the record.

## Storage Considerations

- The database stores the raw IPO record and the required timestamps.
- Computed status and alert state are derived at read time to ensure reproducibility and to prevent stale data from drifting from the business rules.
- The system stores no public-holiday calendar. Weekdays that are public
  holidays count as working days; this is a documented Part 1A limitation.
- Any persistence of computed values must be justified by a clear design reason; otherwise the service layer should compute them at runtime.
